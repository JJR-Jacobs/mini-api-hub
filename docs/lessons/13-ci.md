# 13 — Make every change pass an independent check

**Time:** 15–20 minutes. **Before:** [12 — Containers](12-containers.md), your own GitHub copy and permission to push branches to it. Use the `personal` remote from [lesson 03b](03b-github-and-conflicts.md). Run `git remote -v` and verify it points to your own repository before pushing. You can practise the local portion without a GitHub account.

**Continuous integration (CI)** runs repeatable checks when code changes. A green check tells you the configured checks passed for that revision. It does not prove every behaviour or deploy the app.

## Do: read the workflow

Open `.github/workflows/ci.yml`. Locate:

- `push` and `pull_request`, which decide when checks run;
- the Windows and Linux test matrix;
- `npm ci`, `npm run check` and `npm test`;
- the independent container build;
- read-only repository permissions and immutable action commit hashes.

An **action** is reusable workflow code. The long hash selects one exact revision. The nearby version comment helps a reader identify its release family. Dependabot can propose reviewed updates to these pins.

## Break a real expectation

```powershell
git switch -c lesson/ci-failure
```

Open `tests/recovery.test.js`. Temporarily change the expected live order count from `2` to `99`. Run `npm test` and observe a failing assertion. Keep this deliberate failure only on your practice branch.

```powershell
git add tests/recovery.test.js
git commit -m "Practise reading a failing CI assertion"
git push -u personal lesson/ci-failure
```

Open a pull request in **your own repo**. On its checks page, open the failed test job and find the assertion. Compare its message with your local failure. Do not merge the broken practice commit.

## Fix it and verify

Restore the expectation to `2`, run the checks locally, then commit and push the correction. The pull request should now show passing checks. Compare the commit SHA with the revision being checked.

An intentionally wrong expected count is a simple CI exercise, not a useful production test. In normal work, keep the expected result tied to a requirement and add tests for the behaviour you change.

**You are done when:** you can find a job's logs, explain a failure, fix it without deleting an assertion, and point to the passing check for the corrected commit. Record the PR URL and test command. Close the practice PR or merge only its corrected final state.

**AI prompt:** “Explain this failed assertion from the CI log. Compare it with the requirement before suggesting any code or test changes.”
